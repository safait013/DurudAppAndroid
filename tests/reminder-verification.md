Alarm reminder implementation and verification — 2026-09-12

Scope: Settings → Notifications user reminders and the built-in Friday sunset reminder. No commit, push, reset, revert, or stash was performed. Existing unrelated workspace changes were preserved.

1. **Root cause.** The old implementation already attached a direct full-screen Activity PendingIntent. However, its `setSilent(true)` made AndroidX assign a silent notification group and suppress alerts for the child notification. Android SystemUI explicitly rejects full-screen intents with suppressive group-alert behavior. This is a confirmed source defect explaining a notification that only opens the Activity when tapped. Missing full-screen/exact permissions could additionally cause fallback; no logs from the affected phone were available to establish that phone's permission state. The old controller also used system ringtones and stopped after 120 seconds. See [AndroidX notification construction](https://raw.githubusercontent.com/androidx/androidx/androidx-main/core/core/src/main/java/androidx/core/app/NotificationCompatBuilder.java) and [Android SystemUI full-screen decisions](https://android.googlesource.com/platform/frameworks/base/+/ca1943b2c3c99308185c31044db6156c9313442d/packages/SystemUI/src/com/android/systemui/statusbar/notification/interruption/FullScreenIntentDecisionProvider.kt).

Tests/documentation: `tests/ReminderSchedulerTest.java` is exercised unchanged; `tests/reminder-scheduler.test.ps1`, `tests/reminder-ui.test.cjs`, `tests/hijri-refresh.test.ps1` (Friday route stub only), new `tests/FridayReminderTest.java`, `tests/ReminderControllerTest.java`, `tests/reminder-controller.test.ps1`, and this report. A before/after SHA-256 audit of 111 pre-existing main-source/assets/resources files confirmed changes were limited to the listed production files; religious content, fonts, pronunciation audio, WAV, and Hijri implementation files retained their original bytes.

3. **Old versus new flow.** Previously: receiver → short foreground controller → grouped-silent notification → automatic full-screen could be suppressed → tap opened Activity; controller used a system tone and expired after two minutes. Now: AlarmManager → receiver validates and records occurrence → schedules next recurrence → shared controller posts an ungrouped HIGH alarm notification with direct full-screen intent and immediately starts the selected alert → Android opens the Activity when permitted → visible Activity binds controller and removes the temporary notification → Dismiss clears only the active occurrence.

4. **No tap needed for normal delivery.** Ring/vibration start from the receiver-started service, independently of Activity creation or contentIntent interaction. The notification has `CATEGORY_ALARM`, `PRIORITY_MAX`, and direct `setFullScreenIntent(activityPendingIntent, true)` when allowed. contentIntent remains a legal fallback. If Android denies both background-service execution and automatic full-screen access, only the legal notification fallback is possible; the app does not claim to bypass those restrictions.

5. **Screen off / locked.** The Activity uses `setShowWhenLocked(true)` and `setTurnScreenOn(true)` on API 27+, equivalent window flags on API 21–26, and keeps its visible screen on. It is non-exported, singleTask, in its own excluded-from-recents task. There is no keyguard-dismiss/unlock request and no background `startActivity()` workaround. These paths are source/build verified, not physically tested.

6. **Exact audio resource.** Ring opens `R.raw.durood_premium_soft_ting_ting`, from the existing `app/src/main/res/raw/durood_premium_soft_ting_ting.wav` (59,578 bytes). The file was verified and not changed. No system alarm/ringtone URI or pronunciation audio is used.

7. **Ring lifecycle.** One MediaPlayer uses `USAGE_ALARM`/sonification, loads the bundled WAV using its resource descriptor, prepares asynchronously, and loops. Dismiss/replacement/destruction releases it immediately. Prepared callbacks validate controller identity and the active occurrence, so a late callback cannot restart dismissed playback. Loading/preparation errors are logged and leave the visual alarm available. There is no application-defined two-minute expiry.

8. **Vibrate.** No MediaPlayer is created. One repeating `{0, 600, 500}` waveform starts from the controller; Dismiss/replacement cancels it. Modern VibratorManager/VibrationEffect and the supported legacy path are retained.

9. **Silent.** The same alarm notification and Activity path run, with no player and no vibration. Silent mode is not implemented using the suppressive `setSilent(true)` notification grouping option.

10. **Temporary notification removal.** Notification ID `6200` is shared only by the single active alarm. Once the Activity is resumed with content installed and bound to the controller, the service calls `stopForeground(true)` and cancels that exact ID. Binding to the visible Activity keeps the same controller alive without a foreground notification. Dismiss repeats cleanup and stops the service; unrelated IDs are not cancelled.

11. **Mandatory notification limitation.** Android requires posting the full-screen-intent notification. It can briefly appear before the Activity is visible. If the user presses Home, the controller returns to foreground service mode with the mandatory dismissible alarm notification while sound/vibration continues; this notification does not request another full-screen launch. If the OS does not open the Activity, the notification remains the legal fallback. See [foreground service requirements](https://developer.android.com/develop/background-work/services/fgs).

12. **Permissions audit.** minSdk 21, compileSdk/targetSdk 36. Existing POST_NOTIFICATIONS, USE_FULL_SCREEN_INTENT, SCHEDULE_EXACT_ALARM, FOREGROUND_SERVICE, VIBRATE and WAKE_LOCK declarations are retained. The only added permission is FOREGROUND_SERVICE_SYSTEM_EXEMPTED, for the documented exact-alarm continuation service type, including haptics-only alarms. The service declares `systemExempted|shortService`; runtime selection uses systemExempted when exact access is present and shortService only as a constrained fallback. No location permission, overlay permission, or battery-optimization exemption was added. See [documented service types](https://developer.android.com/develop/background-work/services/fgs/service-types).

13. **First launch / upgrade.** The existing setup screen now shows notification, exact-alarm and full-screen capability status with localized explanations/actions. After setup's existing language recreation finishes, Android 13+ notification permission is requested once if needed. A pending location permission dialog is allowed to finish first. Asked/explanation markers prevent repeated denial prompts. Existing users receive a one-time explanation with an action to the existing Notifications screen; setup, language, preferences and databases are not reset. Returning from system settings rechecks capability and reschedules. Friday controls are visible independently of the user-schedule enable switch.

14. **Exact timing.** User schedules retain the existing weekday/index one-shot AlarmManager design, using setExactAndAllowWhileIdle (or setExact on older Android). Friday uses the same exact scheduling pattern. Missing/revoked exact access uses setAndAllowWhileIdle/set with a logged delayed-delivery warning and saved preferences intact. No polling, WorkManager loop, or permanently running scheduling service was introduced. A fallback delayed beyond Friday sunset is skipped instead of ringing after the intended window. An in-flight Friday delivery is preserved during ordinary cache/resume refreshes.

15. **Full-screen capability.** API 34+ checks `NotificationManager.canUseFullScreenIntent()`; earlier versions use the manifest capability. The settings action opens ACTION_MANAGE_APP_USE_FULL_SCREEN_INTENT when needed. Exact access opens ACTION_REQUEST_SCHEDULE_EXACT_ALARM; notification access uses the runtime dialog or appropriate app/channel settings. HIGH channel availability is included in setup status. The dedicated versioned channel `user_reminder_alarms_v2` has HIGH importance and null sound/no vibration. The builder is ungrouped, with null sound/vibration/defaults, so the controller exclusively owns alerts.

16. **Friday default.** `FridayReminderScheduler` owns one stable built-in definition and one upcoming occurrence. PendingIntent request code `6300` and action `com.darood.app.FRIDAY_SUNSET_REMINDER` are separate from user requests `4000 + weekday*100 + index`, app updates, and Hijri notifications. Occurrence IDs are `friday:<local-date>:<trigger-millis>`. Friday uses the existing shared Activity/controller, Ring mode, and the requested localized English/Bengali/Urdu title and message.

17. **Friday time calculation.** Every target Friday uses its local sunset minus exactly `900000` milliseconds. It reads the existing HijriCache location/day data, accepts matching cached local sunset/timezone data, and otherwise reuses `HijriMath.sunsetApproxMillis` with known coordinates. It never calls the no-location fallback. The matching local date is checked, including neighbouring UTC solar dates at the international date line. Offline approximation is logged. Missing location or unreliable polar approximation defers scheduling until reliable cache data is available; no hardcoded time or assumed city is substituted.

18. **Default enabled / persistence.** Initialization and enabled keys are separate and persisted in existing app_settings. New installations and upgrades initialize the definition once, default enabled, while preserving any explicit enabled value already present. Initialization never writes the regular user schedule JSON.

19. **User disable.** The existing Notifications screen has a Friday switch labelled with its sunset-minus-15-minutes schedule and Ring mode. Turning it off persists the choice, removes its pending alarm and dismisses an active Friday occurrence if applicable. Reopening settings, launching again, and reboot restoration cannot re-enable it. Turning it off does not disable user-created reminders.

20. **Rescheduling.** The next Friday is calculated before the active occurrence starts, so Dismiss leaves next Friday scheduled. The existing boot/package replacement and clock/timezone/exact-access restoration paths include Friday. Startup initializes the definition without overwriting a receiver occurrence during cold process creation. An Application-owned listener observes existing sunset/location cache writes and recalculates Friday, without changing Hijri logic or making a second network request. A local date-change receiver and foreground rescheduling also refresh it. Boot clears old active state and restores future alarms only.

21. **Informational notifications.** Hijri Check/New Hijri Month and App Update retain their normal receiver branches/channels/builders. They do not enter ReminderAlarm. Production Hijri implementation files and the existing update-notification methods were not edited. The existing Hijri regression suite passed 86 checks against API/Room/Android doubles.

22. **Duplicates / replacement.** Existing user revision/due/handled validation is preserved. Friday checks the persisted due/date and handled local date before delivery; stale/duplicate deliveries cannot start a second alert. Stable PendingIntents update one future occurrence. The controller reuses its active instance, releases an old mode before replacement, ignores duplicate starts/rebinds, and guards stale Dismiss/prepared callbacks. Activity recreation rebinds instead of creating a second player. Controller tests also cover permission loss while a surface is already visible.

26. **Remaining Android/OEM limits and device checklist.** Full-screen permission, notification/channel settings, DND, alarm volume, exact access, Doze and OEM behavior remain under Android/user control. Android commonly shows a heads-up banner on an unlocked phone even when full-screen access is granted; locked/off states can launch the Activity. Force-stopping the application differs from ordinary process death and can suppress scheduled delivery. Without exact access, Android may deny background controller startup; if a short-service fallback runs without a visible Activity, its OS timeout stops audio/haptics and retains a legal notification instead of crashing. With exact access, or while bound to the visible Activity, there is no application timeout.
